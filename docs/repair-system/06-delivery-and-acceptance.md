# 开发规范、阶段计划与验收

## 1. 开发方式

设计基线已经交付，当前以本目录为基线，从第 1 阶段逐步实施；每阶段保持可运行、可验证，不一次性重写全部代码。已完成阶段 1–6，当前实现和验收证据见 [最终交付记录](13-final-delivery.md)，前期记录保留为实施历史。产品暂称“门店设施报修”，正式名称后续再定，不影响包结构和接口前缀。

现有未提交改动、密钥、本地配置、旧数据库和已准备的部署文件都保留。旧校园项目停止上线准备，本任务不部署任何新旧服务、不修改服务器、不实际下单、不发送外部消息、不用真实订单图调用 OCR。

## 2. 后端组织与规范

建议目录：

```text
com.gaofeng
├── auth / user / profile        # 经解耦后复用
├── common                      # 错误、校验、限流等共享基础
└── repair
    ├── bootstrap               # RepairApplication、运行配置、初始化命令
    ├── access                  # 成员、角色、门店范围、邀请
    ├── store                   # 门店
    ├── asset                   # 设施台账和分类
    ├── ticket                  # 工单、状态机、过程、验收
    ├── procurement             # 采购、明细、收货、费用
    ├── attachment              # 私有附件与存储适配器
    ├── ocr                     # OCR任务、供应商接口、规则抽取
    ├── notification            # 站内通知、邮件任务、超时提醒
    ├── report                  # 总部统计与导出
    └── audit                   # 管理动作审计
```

每个业务包按 api/dto、service、domain、mapper 划分；Mapper XML 放 `resources/mapper/repair/`。Controller 不持有 JdbcTemplate、不直接编排跨表事务、不接受数据库实体作为任意更新请求。Service 实现明确用例，状态机采用枚举和显式允许迁移集合，不用散落的 magic number。

DTO 使用 Jakarta Validation，禁止把 @Valid 当成业务权限检查。数据库 SQL 参数绑定、排序白名单。新增业务代码使用构造器注入和类型化响应，不沿用旧校园模块的大量 Map<String,Object> 作为外部合同。

repair 运行模式显式隔离旧业务扫描；不依赖启动全部应用后再关闭菜单。共享配置的移动、应用入口切换、旧模块退役分别做可审查的改动；启动类和打包 mainClass 只在该阶段统一修改并校验。

日志包含 requestId、ticketId、action、actorId 和失败分类；不打印密码、JWT、邀请 token、OSS/OCR 凭据、完整采购图片或联系方式。错误响应不泄露数据库语句。

## 3. 前端组织

新增 `features/repair`，按 session、tickets、procurement、ocr、reports 等组织组件/服务/类型；保留已有共享布局、API 客户端与认证基础。门店报修和工程师待办优先适配手机；总部采购/OCR 对照及汇总优先适配桌面。

所有权限来自 repair session 与后端 allowedActions。前端菜单隐藏用于用户体验，后端权限必须独立可测。采购完整 DTO 与材料摘要分开定义，避免把字段隐藏当成数据隔离。

不把旧 Coze/AI/社区聊天依赖带入新工作台。提取可复用组件时保留旧行为回归证据，明确新页面不再强制填写生日/头像。

## 4. 分阶段交付

| 阶段 | 实施内容 | 退出条件 |
| --- | --- | --- |
| 0 设计基线 | 场景、复用、状态、表、接口、OCR和验收设计 | 文档链接有效、状态/字段/权限一致；该阶段未改业务源码 |
| 1 基础隔离与身份 | repair 启动入口；新库迁移；账号/邀请/角色/门店范围；认证解耦；会话与内部登录页面 | 只依赖 MySQL/Redis/本地私有文件即可启动；不访问 Kafka/ES/Canal/AI/OCR；开放注册被拒绝；三角色和停用生效 |
| 2 门店设施与报修主线 | 门店/分类/设施，私有附件，提交、审核、派单、接单、开工、结果、验收；先打通无需采购分支 | 三个角色能完整演示一张无需采购工单；状态、跨店权限、并发与幂等测试通过；未实现的采购分支不返回假成功 |
| 3 手工采购与收货 | 采购草稿/明细/确认下单、材料摘要、分批收货、开工门槛、替换资产、费用确认 | 不依赖 OCR 也能完成配件维修与替换两条业务链；重复收货不超量，材料不到不允许开工 |
| 4 OCR 辅助 | OrderOcrClient/Fake、任务领取/恢复、字段候选、截图对照确认、一个实际供应商适配器 | 合成样本及失败场景全部通过；缺配置时手填可用；实际服务是否联调单独记录，不能用 Mock 结果声称真实 OCR 已通过 |
| 5 通知、超时与报表 | 站内通知/未读、可选邮件任务、超时提醒、总部汇总及 CSV、手机界面收尾 | 汇总与已知测试样本对账；邮件失败不影响工单；多实例不重复提醒；导出不越权或重复累计 |
| 6 清理与总验收 | 旧模块/源码/测试退役；去掉不用依赖；新 README/本地运行说明；完整浏览器验收与打包 | 仅 repair 功能可达；不含旧社区/AI入口；完整编译、测试、前端构建、打包检查通过，仍不部署 |

阶段 1 的新库迁移可以分批落地，不要求第一阶段一次写完所有表。迁移依赖应完整：引用用户/门店的表先建被引用对象，后建外键；未来表的关联列可在后续迁移补约束。

现有 Spring Boot/JDK 保持为改造起点。版本升级若需进行，应在可运行基线后独立评估并提交，不与报修业务重写混在一起。新增 Flyway、OpenAPI 或 OCR SDK 版本按实施时官方文档与依赖树核对，不能直接照搬参考仓库的旧版本。

## 5. 必须覆盖的验收用例

### 5.1 业务与权限

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| R01 | A 店管理员读取/报修 B 店设施，或修改请求中的 storeId | 404/403；列表、总数、附件、导出均不泄露 B 店信息 |
| R02 | 普通门店账号提交 role=HQ_ADMIN 或直接请求总部 API | DTO 不接受提权字段；操作拒绝，无数据变化 |
| R03 | 改派工程师后旧工程师用未过期 JWT 访问 | 失去工单与图片访问权；原操作历史仍保留 |
| R04 | 总部停用账号、并发停用最后两个总部账号 | 停用成员下一次业务请求拒绝；始终至少保留一个有效总部管理员 |
| R05 | 无采购、配件采购、替换设备三条流程 | 分别按合法状态完成；替换不覆盖旧设施型号 |
| R06 | 已下单后尚未到货就接单/开工 | 可接单/约时间；开工返回 MATERIALS_NOT_READY |
| R07 | 门店/工程师读取订单截图、OCR、采购价格 | 拒绝；材料摘要仍正常可用 |
| R08 | 验收退回后再次维修/验收 | 历史结果保留，时间线连续，未提前恢复资产 |
| R09 | 门店/分类停用且仍有未结单 | 新提交拒绝，旧单按授权继续完成 |
| R10 | 旧校园 API、开放注册、旧匿名资源访问工单图片 | 新入口不注册旧业务；工单图片始终按权限读取 |

### 5.2 一致性与外部依赖

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| C01 | 两人同时提交同资产故障 | 最多一个活动资产工单；另一请求明确冲突 |
| C02 | 同 key 重试与同 key 不同 body | 前者回原结果无重复数据；后者 409 |
| C03 | 两个总部同时派单、收货重复提交、超过剩余数量 | 无双重受派、无超收、无半次成功 |
| C04 | 工单事务在插事件/通知时故障 | 状态、资产、附件绑定、采购和费用按整笔事务回滚 |
| C05 | 替换设备验收被重复请求 | 只建一个新资产，旧资产只退役一次 |
| C06 | OCR 超时/限额/错误图片/多商品/缺型号 | 明确状态和候选，手动填写可继续，不编造字段 |
| C07 | OCR 结果到达时采购草稿已被另一人编辑 | 不自动覆盖；应用旧版本返回冲突 |
| C08 | worker 被停止后重启、旧租约结果迟到 | 能恢复，旧 worker CAS 失败，不污染新任务 |
| C09 | OSS 失败、数据库失败、过期暂存图、他人图片 ID | 不产生可用的错误绑定；孤儿清理不越出 repair 前缀 |
| C10 | SMTP 不可用、重复超时扫描 | 业务正常提交；持久化重试/告警，不重复创建站内通知 |
| C11 | 多明细、多事件、多次收货汇总 | 采购和费用不因 join 重复计数；分母为零时比率为 null |
| C12 | 公共资源签名过期或权限已撤销 | 到期无法继续读取；只允许约定 60 秒的已签名窗口 |

### 5.3 界面验收

桌面和 390px 手机宽度检查：报修图片预览、长品牌型号、采购多明细、OCR 左右对照/手机切换、工程师状态按钮、错误重试、保存中重复点击、版本冲突输入保留、门店切换、未读通知、空报表与导出上限。

浏览器端到端至少执行一次完整配件流程、一次替换设备流程、一次无需采购流程、一次跨店越权失败流程。自动化使用合成数据；真实订单截图、真实邮件或收费 OCR 联调必须单独明确测试范围后执行。

## 6. 测试与记录规范

单元测试用于状态迁移、规则抽取、金额计算等确定性规则；接口测试覆盖身份、范围、错误码；真实 MySQL 集成测试用于唯一约束、锁、事务回滚和并发，不能仅凭 H2/Mock 证明 MySQL 一致性。Redis 复用现有隔离测试方式；OSS/OCR/SMTP 默认替身，不主动访问真实业务资源。

建议新增测试类：RepairAccessTest、RepairSecurityTest、RepairWorkflowIntegrationTest、ProcurementReceiptIntegrationTest、OrderFieldExtractorTest、OcrJobRecoveryTest、RepairAttachmentAuthorizationTest、RepairReportIntegrationTest。名称可按最终包结构调整，验证目标不变。

每阶段记录代码范围、迁移版本、测试命令、成功/失败数量、浏览器截图和未完成项。项目历史的 75 项测试、资料完善的 13 项测试均属于旧范围，不能当成本系统已验收。

只运行与阶段相关的检查；通过后不无意义重复全量真实外部服务测试。修改共享认证/存储时补跑对应历史回归。完成新业务或依赖清理时再跑整体检查。

## 7. 阶段完成定义

完成一个功能意味着：文档/接口合同已同步，迁移可复现，权限检查在后端，异常路径有反馈，关键并发不变量被验证，前端可操作且失败不丢输入，日志可追踪且不泄密。

仅有 CRUD、模拟数据页面、始终返回成功的 OCR、只有 happy path 的演示都不算该阶段完成。没有真实联调的服务明确写“未验证”，不以截图或单次启动代替完整验收。
